# H-03 - проверка публичных метаданных одного PubMed-исследования

Частичная реализация [Issue #4](https://github.com/MikeMoore1337/hermes/issues/4).
Модуль `research_scout.pubmed_fetch` не связан с существующим новостным
конвейером YFC, не запускается по расписанию и не использует Hermes Agent,
Cloudflare, платные API, пользовательские секреты или Telegram.

Принудительные технические ограничения:

- Вход - только один числовой PMID; невозможно передать произвольный URL.
- HTTPS только на `pubmed.ncbi.nlm.nih.gov:443` и путь вида `/12345678/`.
- DNS должен вернуть **только публичные** IP; внутренние/loopback/link-local
  адреса вызывают отказ. TCP идёт на проверенный IP, TLS выполняет обычную
  проверку сертификата и имени хоста, таким образом не допускается повторный
  DNS lookup при подключении.
- Нет внешнего прокси, редиректов, API ключей, повторных запросов. Только GET,
  тайм-аут сокета 8 секунд, максимальный ответ 256 KiB, HTML без сжатия.
- Выход содержит лишь публичные `citation_*` метаданные: title, PMID,
  DOI и кандидат даты публикации. Из текста тела страницы ничего не берётся.
  Несовпадение PMID, конфликт metadata, подозрительное внедрение инструкций
  и некорректные поля блокируются.
- Даже успешный ответ обозначается `UNVERIFIED_METADATA`, потому что
  ни истинность утверждений, ни дизайн исследования, ни состояние публикации,
  ни лицензионные права не подтверждены.

Ручной пример (только если публичный DNS/HTTPS egress явно разрешён):

`python3 -m research_scout.pubmed_fetch --pmid 12345678`

**НЕ развёрнуто на VPS и не подключено к Ops Watch**. До production:
проверить отдельную исходящую сетевую политику, rate-limit, несколько
настоящих статей с DOI/PMID и источниками разного типа, затем добавить
подтверждаемые ссылки и отдельный канал доставки. Не дублировать ingestion YFC.


## Фактическая проверка VPS (14.10.2026)

Одиночный пробный запрос PMID 36334240 на Hermes VPS первоначально дал
`UNKNOWN/network_or_tls_error`. Проверка установила: DNS содержит A и AAAA,
маршрут IPv4 есть, а IPv6 default route отсутствует. Исходный алгоритм
сортировки DNS мог предпочесть публичный IPv6 и получить OSError на уровне
подключения. Исправление **предпочитает публичный IPv4**, сохраняя требование
проверять **все** адреса DNS (включая AAAA) и TLS hostname verification.
Если A-записи нет, остаётся публичный IPv6 либо безопасный отказ; никакого
изменения nft/Docker/YFC сетевых правил не требуется.
