# H-01: несоответствие неизменяемого манифеста выпуску Docker v0.21.6

Проверено 15.10.2026 **без обновления образа**, остановки сервисов, чтения секретов и запуска модели. Проверен точно публичный релиз [NousResearch/hermes-agent v0.21.6](https://github.com/NousResearch/hermes-agent/releases/tag/v0.21.6), Git tag object и публичные манифесты в Docker Hub. Это результат независимого сравнения двух реестров, а не утверждение о взломе.

## Доказательства по внешним источникам

- Официальный аннотированный Git-тег `refs/tags/v0.21.6`: tag object SHA `f27cdbce5ab63eafe8633b293a75151409da5769`, указывает на release source commit `818c13be1dc4fd28987e1e881a9408224afd4535`.
- В теле tag object существует `dockerManifestDigest=sha256:9774f4f39a9bb8c2f68ce728ed5e99ddbad282163be56764afacf88ed952b784`, claimTag `rc.4-v0.21.6`, `claimTagObject=99f94588c7dd458fbcc1cbc6db5beb2c2b871bf6`. И `v0.21.6`, и `rc.4` - аннотированные, но **unsigned** (`verification.verified=false`, `reason=unsigned`). Claim tag также указывает на commit `818c13be`; в metadata claim указано `skipTests=true`, `skipBundles=true`. Это не доказывает, что весь релиз абсолютно не тестировался, но означает, что в официальной сборке есть режим пропуска конкретных проверок; на него нельзя полагаться как на дополнительный сертификат качества.
- Проверка публичного Docker Hub на VPS через `docker buildx imagetools inspect nousresearch/hermes-agent:v0.21.6 --format '{{json .Manifest.Digest}}'` выдала **`sha256:55e192fba0cd4fde61142abbff5adeacff40efdb482ccd0ff877924bd274f909`**, а не `9774...`. Дополнительный запрос к неизменяемому `@sha256:9774...` успешно вернул исходный манифест.
- В **текущем** `v0.21.6` два архитектурных манифеста: AMD64 `sha256:32d095e84190ae7266afbb361579e6921f2c633e899f5eacfb88111b9c851a22` и ARM64 `sha256:93b295a42bdb6003e06fb9ce316bd6d4f4c09a93a7a89d263701ec6b1a79b208`.
- В **квитанции** `@sha256:9774...`: AMD64 `sha256:ffa4fbb471c2bc8c85fbcfc629347585cc1586c86d2e6db465d01203ce696d95` и ARM64 `sha256:7e36c10955df8bf957fbb034279770db17c5feab1733637608d1a1d9aceb8193`.
- Рабочие предыдущие проверки Docker проводились на текущем AMD64 image digest `32d095...`, который локально создан `2026-10-08T06:14:28Z` и содержит `/opt/hermes/install-stamp.json: commit=a28a5d03a9fa60418db5f44f3436fa2aa029c8f2, baseVersion=0.21.6, distribution=docker, source=ci`. Это **не** тот же компонент, что AMD64 `ffa4...` из релизной квитанции. Нельзя переносить успешные нагрузочные/прикладные проверки старого образа на другой образ без повторной приёмки.
- В официальном `.github/workflows/docker.yml` для релиза предусмотрена передача проверенных архивов Docker из стадии тестирования без пересборки (`docker save` / SHA256 / `docker load`), запись `GITHUB_SHA` в `identity.json` и проверка перед публикацией. Однако метка version tag в registry после публикации **не соответствует** receipt manifest. Причину (предыдущий кандидат, переиздание тега, некорректное продвижение, иной сбой) установить только из сравнения манифестов **невозможно**.
- Отсутствие подписанной полной SBOM, attestation и удостоверенной цепочки source commit -> image digest остаётся отдельным блокирующим условием.

## Проверка, встроенная в Hermes

[Скрипт](../../scripts/verify_upstream_release_receipt.py) не меняет файлы или настройки VPS. Без флага `--execute` нет ни обращения к Docker, ни сети:

```bash
python3 scripts/verify_upstream_release_receipt.py
# {"status":"NOT_EXECUTED"}

python3 scripts/verify_upstream_release_receipt.py --execute
# Статус RELEASE_RECEIPT_MISMATCH или UNKNOWN; exit 2 в обоих случаях.
```

В режиме `--execute` делает ровно три закреплённых `docker buildx imagetools inspect` над **публичными метаданными** `nousresearch/hermes-agent:v0.21.6` и `@sha256:9774...` через установленный Docker. Не делает `pull`, `build`, `push`, `run`, `login` и не обращается к реальным моделям. Установленный Docker может использовать стандартную локальную конфигурацию реестра при анонимном чтении, скрипт **не принимает и не выводит** её. Строгая схема: ровно 2 платформы `linux/amd64` и `linux/arm64`, лимит ответа 24 KiB, таймаут 18 секунд на запрос, без повторов и подстановок URL/тегов. Вывод только SHA, фиксированные статусы и строгие булевы признаки, никакого raw stderr/случайных ссылок.

**Даже если публичный тег когда-нибудь совпадёт с неподписанной квитанцией**, статус останется `MATCHED_BUT_PROVENANCE_UNVERIFIED` и `resident_agent_allowed=false`. Это контрольный диагностический механизм, **не** команда запуска AI. Обновление внешнего тега требует отдельного доказательства источника, не слепого `docker pull :latest`.

## Следующие условия снятия запрета

1. Получить от поставщика проверяемую подписанную привязку tag/attempt/source SHA -> tested artifact -> immutable manifest digest или провести свою отдельно воспроизводимую безопасную сборку с анализом отличий. Сверить содержимое исходников и замороженных зависимостей.
2. Получить полную подтверждённую SBOM и проверить уязвимости установленного и возможного нового образа (включая Python venv, OS и сторонние бинарники).
3. Отдельно повторить ограниченные функциональные и нагрузочные испытания **ровно того digest**, который предлагается к запуску, и подтвердить нулевой риск списаний по провайдеру.
4. До прохождения этих условий не включать `hermes-agent-sandbox.service` и выделенный прокси. Новости, Ops Watch, CI watcher и Research Scout работают независимо и **не должны останавливатьcя**.

Производитель мог обновить `:v0.21.6` после момента проверки; текущий вывод актуален на указанное время. Не утверждаем злонамеренную подмену или доказанную атаку.
