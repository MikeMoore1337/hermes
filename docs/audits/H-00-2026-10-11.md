## 4. Границы ресурсов и допуск нового Hermes Agent

Реальный ресурсный guard в `deploy/hermes-discovery/hermes_resource_guard.py`:

| Порог `separate-vm` | Факт | Итог |
|---|---|---|
| `MemAvailable >= 768 MiB` | ~941 MiB | `ready`, но запас **~173 MiB** |
| `swap used <= 1024 MiB` | ~718 MiB | Запас ~306 MiB |
| `load1 <= 1.50` | ~0.62 | `ready` на снимке |
| `disk free >= 5120 MiB` | ~16865 MiB | `ready` |

Две ограниченные фазы занимают не более **256 MiB/0.25 CPU** discovery и **512 MiB/0.50 CPU** worker соответственно; источник - unit properties и YFC code. `systemd` units выполняются от `root` как host-side оркестраторы, но сами job-контейнеры по контракту non-root UID 10000. Зафиксировано `ProtectSystem=strict`, `PrivateTmp=yes`, `NoNewPrivileges=yes`. Наличие таблицы `inet hermes_egress` и сети `hermes-net` проверено, **полная effectiveness/deny-by-default от новых сетевых процессов не проверена**.

**Решение:** не размещать полноценный второй агентный runtime на Hermes VPS при текущих ресурсах. Даже постоянные дополнительные ~200 MiB могут опустить `MemAvailable` ниже защитного порога и привести к регулярным skip; реальная пиковая нагрузка неизвестна. На YFC VPS запас ещё меньше (~607 MiB) - colocate тоже отклоняется. Это решение по **риску**, не утверждение, что новый runtime обязательно упадёт.

## 5. Возможные варианты размещения

| Вариант | Возможность | Риски / решение |
|---|---|---|
| A. Текущий Hermes VPS | Уже развернуты CLI/Docker/network | **Не рекомендован** из-за guard headroom, swap и влияния на редакционный поток |
| B. YFC VPS | Уже есть production сервисы и сеть | **Отклонить:** MemAvailable меньше порога Hermes + высокая цена конкуренции за ресурсы |
| C. Windows Desktop + Docker Desktop/WSL | Windows-хост показал ~31.1 GiB total, ~9.4 GiB free; WSL выводит `docker-desktop` | **Разрешимо только как локальная dev-проверка**, не как гарантированно автономный production host: Linux runtime/ресурсы/автозапуск не доказаны |
| D. Отдельный Linux runtime/VM | Изоляция deployment и ресурсов | **Предпочтительная production архитектура**; ещё нет выбранного host, бюджета и согласования стоимости. Исходный ориентир 2 vCPU/4 GiB RAM - **гипотеза для нагрузочных измерений**, не спецификация upstream |

Для H-01: сначала offline zero-tool/zero-provider smoke на dev-среде, затем замер ресурсов, расчёт стоимости и отдельный owner GO на независимый Linux runtime. **Ни один production host сейчас не одобрен.**

## 6. Реальная карта полномочий

```text
ТЕКУЩИЙ LIVE (не менять):
  Hermes discovery -> fixed source registry (YFC) -> bounded outbox
  -> hardened editorial worker -> pinned Groq-compatible provider
  -> HTTPS HMAC intake (YFC) -> YFC checks/owner-review -> Telegram

БУДУЩИЙ (пока только проект):
  Independent Hermes Agent (separate host/OS identity)
   |- Ops Watch: разрешённые read-only health and CI metadata
   |- Research Scout: публичные allowlisted sources, no publish
   |- QA Advisor: limited GitHub read-only
   |- Second Brain: НЕТ ДОСТУПА до #386 и отдельного GO
```

**Подтверждённые границы сейчас:** разделение по VPS, hermes UID 10000, read-only workers, pinned releases, HMAC YFC intake, очередь, owner gate. **Пока не доказаны для нового runtime:** enforced capability ACL, egress per-agent, отсутствие прямого доступа к Docker socket/YFC DB/private vault. В H-01 нужно не только документировать, но и **отрицательными проверками** доказать эти запреты до запуска. Конфигурационный `permissions.yml` сам по себе не enforcement.

Запреты H-01: не включать платные провайдеры/ключи, чужие skills, неофициальный subscription proxy, web-shell с широкими правами, привилегированный Docker, подключение private vault, новый публикующий бот и auto-merge/deploy.

## 8. Метод и ограничения

Метод: однократные read-only команды `hostname`, `date`, `uptime`, `free`, `df`, `systemctl show/list-timers`, `docker ps`, `docker stats --no-stream`, `nft list`, `stat`, выборочные JSON-поля health/release и статусы compose. В resource guard вызван только режим `check`, который выдаёт решение; не использован install/reset/repair. Вывод с адресами серверов, приватными конфигами, запросами и токенами намеренно не собирался.

Снимок не охватывает долгосрочные peaks, реальную эффективность egress firewall, сетевое проникновение, права external providers, end-to-end публикации и детальный rollback test. Это отдельная проверка перед H-01 GO или production migration.
