# H-18 / #199 — следующий фиксированный кандидат PyJWT 2.15.1

**2026-10-16. Итог: LOCAL_PYJWT_2151_DERIVATIVE_VERIFIED / RESIDENT_NO_GO.** Новый образ был собран, протестирован и повторно просканирован в локальном Docker Desktop. На VPS не установлен.

Причина корректировки: реальный Trivy 0.76.0 (local cached DB 2026-10-16) после установки PyJWT 2.14.0 в тестовый derivative показал 2 остающихся уязвимости PyJWT: **CVE-2026-101918** и **CVE-2026-102275**. Обе исправлены в версии **2.15.0** по upstream/advisories, актуальный безопаснее тестируемый target — **2.15.1**, опубликованный на PyPI 2026-09-28. Поэтому нельзя считать промежуточную версию 2.14.0 достаточной для закрытия всех известных PyJWT findings.

## Новая версия и supply chain

Локально скачан public wheel `pyjwt-2.15.1-py3-none-any.whl` официальным pip `--no-deps --only-binary=:all:`, SHA256 локального wheel **совпал с hash на официальной HTML-странице PyPI**:

`42d59d631f7768a1028a64c7ff581a9bf7519804daf91fc5b6c56e30eec5e193`.

Информация PyPI указывает Trusted Publishing и verified publish attestation для wheel, но **самостоятельная верификация Sigstore bundle не выполнялась**.

Рецепт `docker/v0222-pyjwt-fixed-candidate/Dockerfile` и безопасный helper `scripts/prepare_v0222_pyjwt_candidate.py` перепинены на **PyJWT 2.15.1** и full SHA256, исходный image exact digest остался неизменным. Дополнительные синтетические tests должны пройти в Linux CI. **Фактически выполнено позже 16 октября:** Docker Desktop восстановлен. Offline-подготовка 3-файлового build-context через SHA-pinned helper прошла успешно. Настоящий `docker build --pull=false --network none --platform linux/amd64 --no-cache` завершился SUCCESS; SHA256 wheel PASS, `pip --no-index --no-deps` заменил **2.13.0 → 2.15.1**, `git apply --check` и применение guard patch PASS, `pyproject.toml` закреплён на `PyJWT[crypto]==2.15.1`. **Новый** local image ID `sha256:90e878c4af899364fb56be9e7c4f5e96ca06c4741b6c94cc79260f07f919ebe9` (не publisher signature). Старый `sha256:5f1a...` относится только к промежуточной версии 2.14.

## Фактические проверки нового PyJWT 2.15.1 образа

1. **Синтетическая криптография:** реальный PyJWT 2.15.1 внутри локального контейнера (только --network none, read-only, nonroot, no-new-privileges) принял корректную RS256-подпись временного ключа RSA-2048 и отклонил изменённый payload с оригинальной подписью (jwt.InvalidSignatureError), exit 0. Не использовались реальные ключи и никакой LLM.
2. **Native tool policy:** реальный bounded mock comparator против исходного official v0.22.2: `PATCHED_NATIVE_TOOL_POLICY_BOUNDED_PASS`, `original_gap_reproduced=true`, `patched_checked_paths_blocked=true`, `allowed_synthetic_paths_work=true`, `model_executed=false`, `real_tool_executed=false`, `resident_agent_allowed=false`. Это не доказательство защиты всех реальных OS/MCP инструментов.
3. **Trivy 0.76.0 + та же сохранённая vulnerability DB (UpdatedAt 2026-10-16), --offline-scan, --skip-db-update:** реальный повторный локальный scan image SUCCESS. Raw report остаётся только вне Git, SHA256 `6da0be9e77c687d54225ed44c5a15507962f6c0ac5b7d8c8eaaee2bc11ea7adb`.
