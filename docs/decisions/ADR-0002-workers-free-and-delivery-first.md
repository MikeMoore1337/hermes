# ADR-0002: Workers Free подтверждён владельцем; delivery-first для Hermes v0.22.2

Дата: 2026-10-17  
Статус: **принято владельцем; действующее проектное решение**  
Область: Hermes Agent, H-10 #62, H-01 #33, H-18 #185/#199, ChatGPT, Codex, ревью и дальнейшее планирование.

## Почему принято решение

В нескольких последовательных проверках команда повторно требовала подтверждать уже предоставленные скриншоты Cloudflare и ставила реализацию Hermes в зависимость от долгого аудита сторонних пакетов. Владелец подтвердил: проект необходимо завершать в сжатые сроки. Расширенный security/supply-chain аудит и ожидание исправлений upstream-библиотек выполняются **после реализации основной функциональности**, а не блокируют разработку.

## Решение A: Cloudflare Workers AI Free - owner-confirmed

**Исторический факт, подтверждённый владельцем, не запрашивать повторно без изменения обстоятельств:**

- Cloudflare Dashboard → Billing → Subscriptions: **Workers Free / Active**, доступно предложение Upgrade to Workers Paid.
- Cloudflare Dashboard: **No payment method on file**.
- AI Gateway: исходный onboarding-экран, **нет пользовательского настроенного gateway**; UI объясняет, что default gateway может создаваться автоматически при первом специальном вызове. Это **не** свидетельствует о подключённом платном Unified Billing.
- Ранее в том же сеансе Cloudflare Workers AI Usage: **60.89 / 10 000 Neurons** и модель `@cf/openai/gpt-oss-20b`.
- Отдельные ручные вызовы этой модели уже получали HTTP 200; это functional evidence, а не доказательство суммы списаний.
- Первичный подробный акт: [Issue #62, comment 6201988952](https://github.com/MikeMoore1337/hermes/issues/62#issuecomment-6201988952). Владелец повторно прислал скриншоты 17.10.2026 и потребовал прекратить повторные запросы доказательств. Скриншоты с идентифицирующей информацией не загружаем в git.

**Операционное правило:** при обычном планировании, разработке, ревью, CI и исправлении #62/#33 считать существующий аккаунт **`OWNER_CONFIRMED_WORKERS_FREE`**. Не писать `ACCOUNT_FREE_UNVERIFIED` как будто скриншотов не было, не отправлять владельца снова за теми же скриншотами и не создавать новый платёжный/биллинговый токен только ради формальной перепроверки. Три read-only запроса с действующим Workers AI токеном к subscriptions/gateways/entitlements вернули HTTP 403 17.10.2026; это недостаток прав для чтения, **не отмена owner attestation**.

**Отдельные технические факты, которые не следует подменять подтверждением аккаунта:** соответствие секретного Account ID аккаунту на снимках не проверено независимым способом; фактические provider-side Neurons и стоимость прошлых API-ответов не сообщались; будущая смена тарифа или настройки gateway теоретически возможна. Указывать эти данные как `NOT_MEASURED`, а не объявлять доказанные `$0`.

Разрешён только Workers Free, `@cf/openai/gpt-oss-20b`, без платного fallback, upgrades, AI Gateway Unified Billing, кредитов и автоповторов. Рабочая **техническая** проверка свежести снимка остатка Neurons/UTC-даты и локальных лимитов, если она требуется текущим кодом перед новым live-вызовом, **сохраняется**. Не выдавать исторический скриншот за свежую ежечасную телеметрию. При реальном изменении тарифа, способа оплаты, выбранного аккаунта/модели либо маршрута через gateway статус пересматривается; без такого события повторно не поднимать тот же вопрос.

## Решение B: Hermes v0.22.2 - функциональная поставка прежде расширенного аудита

Владелец явно установил приоритет на 17.10.2026: **выполнить проект быстро, работать с имеющимся закреплённым v0.22.2 и текущими библиотеками. Полный аудит безопасности провести после завершения основного функционального объёма.** Не откладывать реализацию, PR, обычные тесты и доставку уже одобренных сервисов из-за ожидания новой upstream-версии, полного SBOM/аттестации, устранения всего списка CVE или долгого сравнения сканеров.

Практическая граница:
1. **Сейчас:** реализуем функции и инфраструктуру, устраняем обнаруженные *функциональные* неисправности, фиксируем версию образа, используем текущий код, запускаем адресные тесты, проверяем, что релиз работает и откатывается. Known native tool dispatch gap из #33 - конкретный дефект исполнения разрешений: при подключении инструментов его нужно исправить или ограничить доступные capability; не превращать в бесконечный комплексный аудит.
2. **В фоне/после основного релиза:** #185, #199 и provenance/CVE/licence/SBOM, масштабный permission/penetration аудит. Фактические находки не скрывать, но **не делать ожидание фиксов сторонних библиотек общим блокером development/merge**. По результатам работ скорректировать приоритеты.
3. **Не меняется от этого ADR:** запрет новых расходов, платных providers/fallback, неразрешённых публикаций, доступа к чужим данным и разрушительных действий; не отключать существующие ресурсные/сетевые ограничения; не считать зелёный CI разрешением включить resident agent, дать shell/MCP/privileged tools или изменять production без предусмотренного владельческого согласования.
4. Для уже разрешённых активных сервисов действует обычный exact-SHA CI → merge → production delivery. Для **нового** постоянного AI Agent активацию согласовать отдельно с владельцем, ограничить доступные инструменты/данные, провести целевые smoke/recovery/resource проверки и задокументировать результат; **не требовать предварительного закрытия всего CVE backlog** только из-за факта его существования.

Это решение об очередности/принятии риска на стадии реализации, **не утверждение, что официальный v0.22.2 не имеет уязвимостей**, и не автоматический перевод `resident_agent_allowed` или `agent_budget/policy.json` в enabled.

## Приоритет при разночтениях

Этот ADR и ссылка на него в корневом `AGENTS.md` отражают **более новое решение владельца** и заменяют более старые формулировки в Issues и checklist, которые требуют заново доказать тариф или дождаться завершения полного аудита **до начала разработки/выкатки уже одобренного функционала**. Исторические отчёты не редактировать задним числом. Когда вопрос касается фактического включения нового сервиса или способности выполнить платный вызов, сначала сверять текущий код и действующий scope разрешений, а не механически переносить старое `NO-GO` на все виды работ.
