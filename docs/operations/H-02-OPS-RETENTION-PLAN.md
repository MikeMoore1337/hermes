# H-02 / #3 — журнал Ops Watch: безопасный read-only контроль роста

Статус 16.10.2026: **планирование архива, без разрешения на архивацию или удаление**.
Каноническая SQLite находится под контролем существующего Ops Watch.
`state`, `events`, `delivery_receipts` и служба отправки Telegram
**не мигрируют**, схему и systemd менять нельзя.

## Где границы

- Метрики: число всех событий, подтверждённых ACK, неподтверждённых,
  исчерпавших retry, и размер SQLite в байтах. Текст сообщений, токены lease,
  chat_id, Telegram message_id, сырой fingerprint и строки БД не возвращать.
- Исходные пороги для **ручного просмотра**, не для удаления:
  ≥ 10 000 ACK-записей или ≥ 32 MiB файла.
- При превышении: `MANUAL_ARCHIVE_PLAN_REQUIRED`. События без ACK,
  исчерпавшие попытки, каноническое `state` и их связи — **не кандидаты**.
  Никакой автоматической политики «хранить N дней» нет.
- При нулевых/малых метриках — `MONITOR_ONLY`. Отсутствие события,
  подтвердившего реальную доставку и естественное восстановление, всё ещё
  не закрывает требование #3.

Инструмент `ops_watch.retention_audit.assess(directory)` переиспользует
`delivery_contract.stats`, проверяет SQLite 0600, владельца ОС, отсутствие
symlink/hardlink и работает только с агрегатами `mode=ro`. Сам CLI
зафиксирован на `/var/lib/hermes-agent/ops-watch` и требует явного
`--inspect`. Без него ответ `NOT_EXECUTED`.
Нет DDL, SQL DELETE, VACUUM, checkpoint, новых БД, ротации, таймера,
сетевых запросов и изменения Telegram отправителя.

Команды:

```bash
# По умолчанию без чтения состояния:
python3 -m ops_watch.retention_audit
# Только операторская read-only оценка, без архивации:
python3 -m ops_watch.retention_audit --inspect
```

## Если порог достигнут — только отдельный owner GO

1. Зафиксировать метрики, свободное место, владельца и штатное состояние всех
   Ops Watch timers/Telegram sender. Проверить, нет ли незавершённых доставок,
   exhausted попыток или потерянных ACK; их **не перемещать**.
2. Утвердить нормативный срок хранения истории с владельцем. Текущая
   документация не предполагает ни автоматического удаления, ни 30/90 дней.
3. Согласовать maintenance window и **отдельный** бэкап всей SQLite с
   сохранением владелец/0600 и проверкой восстановления в чистом изолированном
   контуре. Никогда не переносить текущую базу в публичные CI-артефакты.
4. Подготовить **отдельный** PR миграции/архивирования только ACK-записей с
   доказанной ссылочной целостностью, атомарным откатом и безопасной
   долговременной политикой хранения. До разрешения — НЕ выполнять шаг 4.
5. После независимых тестов восстановления и owner GO — отдельный deploy
   gate. Если архив нельзя безопасно доказать, оставить исторические записи
   и наблюдать размеры.

## Проверки на синтетических данных

Временная SQLite с реальными таблицами Ops Watch и фиктивными receipt:
проверка байтовой неизменности до/после отчёта, порога ACK/объёма,
сохранения unacknowledged, отказа на symlink/0600/неверных параметрах,
отсутствия исходного содержимого инцидентов в отчёте.
Натуральная production авария, бэкап и восстановление **не моделируются
как случившиеся**.

Объём #3 остаётся PARTIAL/OPEN, даже если offline тесты зелёные.
