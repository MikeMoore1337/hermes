# H-02 - безопасное подтверждение инцидентов и восстановления

[Issue #3](https://github.com/MikeMoore1337/hermes/issues/3).

## Реально доказано

1. Получатель Ops Watch в Telegram лично подтвердил живое сообщение `message_id=4` от отдельного бота. Код `send_one` сохранил receipt в **тестовую** SQLite и запретил дубликат, [PR #73](https://github.com/MikeMoore1337/hermes/pull/73).
2. `hermes-ops-alerts.timer` включён на VPS и действительно запускает службу раз в ~10 минут; при пустой рабочей очереди последняя завершается `EMPTY_OR_LEASED`. [Акт](../audits/H-02-autosender-vps-2026-10-14.md).
3. Проверка на VPS 15.10.2026: изолированный `collector.once` с подменённым **только входным состоянием systemd внутри Python** зарегистрировал появление `ops:timer_disabled` и последующее восстановление. Изолированная очередь доставила оба события **только в fake transport**, записала ACK с синтетическими message_id=501/502, повторная отправка заблокирована. [Unit test](../../tests/test_ops_watch_recovery_transitions.py) повторяет это в CI.
4. Настоящего самопроизвольного сбоя, за которым последовала бы полностью автоматическая отправка в Telegram, **пока не было в наблюдаемых данных**. Из пунктов 1-3 нельзя выводить такой факт.

## Операционное ограничение связанного systemd unit (важно)

15.10.2026 в ходе согласованного контролируемого испытания обнаружено: **`systemctl disable hermes-discovery.timer` не только снял автозагрузку, но также удалил символическую ссылку самого unit** в `/etc/systemd/system/hermes-discovery.timer`. Это было связано с тем, что канонический файл живёт в `/opt/hermes/releases/.../systemd`, а в systemd был подключён через ссылку. Скрипт испытания был немедленно остановлен, не удалось создать инцидент: повторно создавать такую неисправность **ЗАПРЕЩЕНО**. Ошибка реального production эксперимента, а не успешный тест.

Восстановление выполнено по **сохранившемуся оригинальному backup symlink** `/etc/systemd/system/hermes-discovery.timer.bak-20260923-stability`; цель `/opt/hermes/releases/hermes-67e906bdb34c-b38bec8a8cf911c1/systemd/hermes-discovery.timer`, права и содержимое канонического файла не изменялись. Выполнены `daemon-reload`, `enable --now`. Независимая перепроверка: unit `loaded/active/enabled`, следующий запуск был назначен, последний запуск news service `Result=success / ExecMainStatus=0`; Ops timers active, nft guard verified, свежий collector ответил `active_codes=[]`, `raised=[]`, `resolved=[]` и рабочая очередь осталась пустой.

**Нельзя** проверять Ops Watch путём остановки/отключения рабочих таймеров новостей, guard, backend или модификации рабочего `/var/lib/hermes/state.json`. Для повторяемости использовать изолированные temp каталоги и mock фактов systemd, в которых автоматически исполняется существующий настоящий обработчик, но никаких сетевых запросов и production записей. Нельзя объявлять такое моделирование подлинным производственным инцидентом.

## Следующая естественная проверка

При следующем **настоящем** нарушении, отражённом доступными Ops Watch источниками, сопоставить запись новой тревоги в `events`, запись реального `message_id` и `acknowledged` в `delivery_receipts`, фактическое сообщение в личном чате и последующее `phase=resolved` при восстановлении. Не добавлять синтетические события в production ради зелёного статуса и не менять критические службы для теста. Статусы, ID и времена публиковать без исходных данных/токенов.


## Ручная сверка записанных подтверждений инцидента и восстановления

После естественного возникновения и разрешения инцидента можно **на чтение** проверить зарегистрированную последовательность в локальной SQLite:

```sh
python3 -m ops_watch.recovery_evidence --code timer_inactive
# NOT_EXECUTED, чтение базы отсутствует

python3 -m ops_watch.recovery_evidence --execute --code timer_inactive
# RECORDED_ACK_PAIR_UNVERIFIED, код выхода 0, если обе записи и ACK имеются
# NO_RECORDED_ACK_PAIR / UNKNOWN, код выхода 2 в остальных случаях
```

Указывается только код из фиксированного `INCIDENT_CODES`, а не произвольный SQL/путь. Чтение через защищённый `SQLite mode=ro`, список ограничен 1000 строк для одного кода, ссылки и права на файл проверяются. Проверяются канонические заголовки/действия, порядок событий, различные положительные `telegram_message_id`, временные метки и статус `acknowledged` у **обеих** записей. Инструмент не читает токен, не отправляет Telegram-сообщения, не меняет подтверждения или SQLite, не вмешивается в systemd.

**Граница доказательства:** `RECORDED_ACK_PAIR_UNVERIFIED` свидетельствует только о **локально записанной** паре new/resolved с квитанциями. Нельзя на её основании объявить доказанными естественное происхождение сбоя, реальное принятие обоих сообщений Telegram или факт их прочтения человеком. Для закрытия #3 нужны независимые системные журналы и естественное событие; синтетический тест такого доказательства не создаёт.

Команда не добавлена в production timer и не развернута автоматически на VPS. Тесты выполняются на временных SQLite и имитированных квитанциях без сети.
