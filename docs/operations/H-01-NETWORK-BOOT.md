# H-01 - восстановление сетевой защиты после reboot

На действующем VPS уже доказаны два bounded Hermes CLI Agent-turn, включая подтверждённый
в SQLite вызов todo_list. Результат зафиксирован в [аудите](../audits/H-01-full-agent-tool-turn-2026-10-14.md).
Данная задача НЕ включает круглосуточный запуск агента.

## Контракт

- Новый `hermes-cloudflare-network-guard.service` запускается **после docker.service**.
- `--ensure` проверяет существующий изолированный мост Docker, подсеть, маршрут и **полное структурное
  содержимое** nft-таблицы hermes_agent_isolation. При существующем идентичном состоянии
  **ничего не меняет**.
- Если отсутствуют правила, они создаются одной атомарной транзакцией nft **до создания**
  отсутствующей Docker-сети. Если существующие правила или сеть отличаются от контракта,
  сервис **отказывает**, не исправляя чужое состояние и не затрагивая YFC hermes_egress.
- Прокси зависит от успешного запуска нового guard unit и не должен стартовать при его
  ошибке. AI Agent сервис остаётся `disabled/inactive`, секреты вне нового сервиса.
- Вне области задачи: изменение существующих YFC units, nginx, Docker defaults,
  сетевых правил других служб или перевод на платный провайдер.

## Проверки до объединения и на сервере

- CI: точная проверка цепочек и правил, отказ при неизвестных/изменённых условиях,
  идемпотентность, fail closed, отсутствие записи при --check.
- На VPS: точный SHA, `systemd-analyze verify`, `--check`, повторные `--ensure`,
  сравнение `nft -j list table` до/после, активность YFC news/ops timer.
- Только после этого можно **включить в автозагрузку один новый guard**, но не AI agent
  и не Cloudflare proxy.
- **Реальный reboot production VPS без отдельной команды владельца НЕ проводить.**
  Поэтому до фактического reboot или безопасной VM-копии статус только
  `boot wiring configured + one-shot recovery check`, не `reboot verified`.

### Восстановление

Новый сервис может быть выключен независимо: `systemctl disable --now
hermes-cloudflare-network-guard.service`. **Не удалять** правила nft, пока существует
изолированная сеть или подключённый контейнер; отключение systemd не является
разрешением на снятие firewall.

Длинные AI-сессии не включены. Для любого ручного запуска требуются текущие
nft/bridge preflight и жесткий ограничитель CPU/RAM/load.


## Дополнительная проверка перед КАЖДЫМ запуском прокси

Системная служба Cloudflare TLS relay дополнительно вызывает команду `ensure_cloudflare_egress.py --check` **непосредственно перед ExecStart**. Она читает всю конфигурацию nft/bridge, ничего не создаёт, не меняет и отклоняет старт при несовпадении. Это защищает от сценария, когда oneshot guard остаётся `active`, а кто-то позднее изменил или удалил nft-таблицу.

Код systemd использует префикс `+` **только для короткой проверочной команды**, которой требуется доступ администратора к nft/Docker metadata; основной Python CONNECT relay всё ещё выполняется под `hermes-egress` с пустым `CapabilityBoundingSet=` и `NoNewPrivileges=yes`. Важно учитывать, что именно эта проверочная команда исполняется с расширенными привилегиями и должна оставаться root-owned, неизменяемой для агента и без обработки внешних данных. Одноразовый вызов самого агента также дополнительно проверяет полную структуру сети через `--check`. 


## Результат фактического VPS-теста

[Акт 14.10.2026](../audits/H-01-network-guard-vps-2026-10-14.md): проверка idempotent повторного вызова guard, полного неизменённого SHA nft-таблицы, systemd dependency, реального старта прокси с `ExecStartPre`, активных news timers и выключенного AI-сервиса. **Реальный reboot всё ещё не выполнялся** и не считается проверенным.

## Реальный reboot выполнен 14.10.2026

По прямому разрешению владельца выполнена реальная перезагрузка VPS. Boot ID изменился, Docker стартовал раньше Hermes network guard, правила были проверены без изменений, новостной и Ops Watch таймеры восстановились и выполнили по одному успешному циклу. AI и proxy не запустились. Подробный [акт и оставшиеся ограничения](../audits/H-01-reboot-recovery-2026-10-14.md). Это закрывает только проверку reboot recovery, а не #33 целиком.
