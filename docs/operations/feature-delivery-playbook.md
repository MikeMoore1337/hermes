# Разработка и проверка изменений Hermes без дополнительного оркестратора

Применяется к реализации задач **этого репозитория**: Ops Watch, Research Scout, QA Advisor, адаптеры и правила. Не является навыком или разрешением на установку в upstream Hermes Agent и не включает его автономный runtime.

## Оценка риска перед работой

| Тип задачи | Нужная проверка |
| --- | --- |
| Малое локальное изменение правил/документации | Существующий Issue, точечные статические проверки и diff. |
| Новое поведение адаптера, несколько компонентов | Проверяемые вход/выход, error/retry/idempotency и источники данных; адресные unit/integration-тесты. |
| Внешний провайдер, секреты, платежи, доступ к YFC/Second Brain, полномочия исполнителя, VPS/production | Сначала ограничения угроз, права и конкретный owner gate. Настоящий вызов/изменение runtime только после отдельного разрешения. |

Глубина анализа не означает отдельную группу агентов. Прежде всего переиспользовать существующий код и штатный GitHub Flow.

## Проверяемое определение результата

Описать в Issue или PR (без собственной БД задач):

- Фактический вход, источник с provenance, разрешённую операцию и ожидаемый результат.
- Критерии `C1` ... `Cn` с наблюдаемым исходом и адресными проверками.
- Какие средства реально обеспечивают ограничения ОС, сети, файлов, инструментов, времени и вызовов. Формулировки в Markdown сами по себе не являются sandbox.
- Ошибки, повтор, дедупликацию, отрицательные permission-тесты и безопасный отказ по применимости.
- Версию/SHA, фикстуры, команды и результаты: `MOCK_ONLY`, `SIMULATED`, `LIVE_VERIFIED`, `PRODUCTION_VERIFIED` либо `NOT_VERIFIED`. Эти слова не взаимозаменяемы.

Проверяющий сверяет исходное требование, настоящий diff и доказательства. Ревью выполняется существующими средствами CI/PR; дополнительный агент подключается только к конкретному вопросу, если он доступен и разрешён. Авторское заключение или зелёные синтетические тесты не доказывают работу внешнего API, реальное восстановление VPS или научную корректность материалов.

## Ограниченный эксперимент

Для новой автоматизации сначала выполнить дешёвую детерминированную проверку в изолированной среде с фикстурами. Указать, какое предположение она проверяет. Не запускать внешнюю модель, сеть или секреты ради отчёта без отдельного разрешения. Если live-проверка запрещена, оставить результат `NOT_VERIFIED` или `BLOCKED`, не подменять симуляцией.

Пределы ресурсов и стоимости должны применяться **реальными** настройками runtime/OS/API. Описание бюджета в Issue не ограничивает вызовы модели или дочерние процессы. Фактические токены и деньги приводить только из достоверной телеметрии; иначе `UNKNOWN`.

## Передача и безопасность

В итоговом PR сообщить, какие критерии выполнены, тесты/проверенный SHA, что осталось не доказано, какие изменения происходили на VPS и кто разрешил их. Не закрывать задачу без необходимых доказательств.

Не устанавливать сторонние `SKILL.md`, исполняемые файлы или архивы на VPS по факту наличия в проекте. Не вводить второй контроллер, очередь, постоянный агент, новый источник состояния, автоматический merge/deploy, провайдера или доступ к private vault. Не переносить новостной поток YFC, права публикации и источники данных. Действующие `AGENTS.md`, модель угроз и owner gates имеют приоритет над этим руководством.
