# Разработка и проверка изменений Hermes без дополнительного оркестратора

Применяется к реализации задач **этого репозитория**: Ops Watch, Research Scout, QA Advisor, адаптеры и правила. Не является навыком или разрешением на установку в upstream Hermes Agent и не включает его автономный runtime.

## Оценка риска перед работой

| Тип задачи | Нужная проверка |
| --- | --- |
| Малое локальное изменение правил/документации | Существующий Issue, точечные статические проверки и diff. |
| Новое поведение адаптера, несколько компонентов | Проверяемые вход/выход, error/retry/idempotency и источники данных; адресные unit/integration-тесты. |
| Внешний провайдер, секреты, платежи, доступ к YFC/Second Brain, полномочия исполнителя, VPS/production | Сначала ограничения угроз, права и конкретный owner gate. Настоящий вызов/изменение runtime только после отдельного разрешения. |

Глубина анализа не означает отдельную группу агентов. Прежде всего переиспользовать существующий код и штатный GitHub Flow.

## Проверяемое определение результата

Описать в Issue или PR (без собственной БД задач):

- Фактический вход, источник с provenance, разрешённую операцию и ожидаемый результат.
- Критерии `C1` ... `Cn` с наблюдаемым исходом и адресными проверками.
- Какие средства реально обеспечивают ограничения ОС, сети, файлов, инструментов, времени и вызовов. Формулировки в Markdown сами по себе не являются sandbox.
- Ошибки, повтор, дедупликацию, отрицательные permission-тесты и безопасный отказ по применимости.
- Версию/SHA, фикстуры, команды и результаты: `MOCK_ONLY`, `SIMULATED`, `LIVE_VERIFIED`, `PRODUCTION_VERIFIED` либо `NOT_VERIFIED`. Эти слова не взаимозаменяемы.

Проверяющий сверяет исходное требование, настоящий diff и доказательства. Ревью выполняется существующими средствами CI/PR; дополнительный агент подключается только к конкретному вопросу, если он доступен и разрешён. Авторское заключение или зелёные синтетические тесты не доказывают работу внешнего API, реальное восстановление VPS или научную корректность материалов.

## Ограниченный эксперимент

Для новой автоматизации сначала выполнить дешёвую детерминированную проверку в изолированной среде с фикстурами. Указать, какое предположение она проверяет. Не запускать внешнюю модель, сеть или секреты ради отчёта без отдельного разрешения. Если live-проверка запрещена, оставить результат `NOT_VERIFIED` или `BLOCKED`, не подменять симуляцией.

Пределы ресурсов и стоимости должны применяться **реальными** настройками runtime/OS/API. Описание бюджета в Issue не ограничивает вызовы модели или дочерние процессы. Фактические токены и деньги приводить только из достоверной телеметрии; иначе `UNKNOWN`.

## Условная оркестрация экспертиз (только разработка)

Сложная задача Hermes может потребовать нескольких **независимых исследовательских
и проверочных взглядов**. Это не означает запуск нескольких экземпляров
resident Hermes Agent: речь исключительно о Codex/ChatGPT/другом клиенте,
который помогает разрабатывать код **этого репозитория**. Источник метода:
[Toolkit QA Orchestra, PR #135](https://github.com/MikeMoore1337/ai-development-toolkit/pull/135)
и [Feature Delivery Orchestra, PR #137](https://github.com/MikeMoore1337/ai-development-toolkit/pull/137).
Оба PR объединены с `main` Toolkit 21.10.2026, но опубликованный выпуск
`v5.4.0` не содержит этих методов. Без подтверждённой загрузки навыков
и реального следа вызова субагентов не утверждать, что методы исполняются
или подключены к resident agent.

- **Обычная правка:** один разработчик, одна целевая проверка, без группы
  агентов. **Рискованная cross-component задача:** до трёх независимых
  направлений только на реальные вопросы: contract/source research, security
  boundaries, risk-based QA; не назначать агента для каждого `SKILL.md`.
- Один ответственный `implementer` меняет **только** свою ветку/PR.
  Аналитики и QA по умолчанию `READ_ONLY`. Утверждённые исправления
  выполняются ответственным исполнителем после сводного решения. Зависимые
  изменения API/schema/fixtures и общие файлы сериализуются.
- Вызванный отдельный subagent отмечается как `ACTUAL_SUBAGENT` или
  `GENERIC_SUBAGENT` только при наличии реального следа инструмента.
  При отсутствии доступа - `SEQUENTIAL`; изменение точки зрения одним ИИ
  не является независимым исполнителем.
- Каждая проверка связывается с критерием Issue, exact SHA, окружением,
  командой и наблюдаемым результатом. CI, unit/synthetic, приватный VPS,
  реальное устройство, production-тест, GitHub merge и разрешение на runtime
  **разные** статусы. `NOT_RUN` и `UNKNOWN` не заменять успешным результатом.
- На реальном примере
  [H15 #448](https://github.com/MikeMoore1337/hermes/pull/448) исходные
  проверки и GitHub CI успешны, однако изменённый Dockerfile сам по себе
  не собирался в рамках этого PR. Остающиеся runtime-тесты относятся к
  отдельной приёмке #445. Это пример границы доказательств, а не
  сертификат исполнения новых агентов.
- После анализа в одном существующем Issue/PR оставить сводный handoff
  без локальной БД: выводы и расхождения, точные результаты, какой runtime
  **не тестировался**, blockers, фактически достигнутый этап и следующее
  действие. Показатели ускорения, токенов/стоимости и качества
  `NOT_MEASURED`, пока нет измерений в реальном клиенте.

**Жёсткие запреты:** новый live/model provider, платные API, resident agent
активация, secrets, новые OS/MCP capabilities, автоматическая публикация,
YFC writes, доступ к private vault или изменение активных сервисов
не разрешаются документами об оркестрации. Никакого второго CI controller,
постоянных субагентов, демонов и авто-merge/deploy.

## Непрерывная безопасная доставка (решение владельца 16.10.2026)

**Предпочтение владельца:** готовые безопасные PR не должны накапливаться.
Если текущая задача и среда утверждены, exact HEAD и обязательный CI успешны,
замечаний, конфликтов и нарушений прав нет — исполнитель проверяет diff,
объединяет PR и доставляет только разрешённую часть изменений. После этого
фиксирует merge SHA, версию на VPS, реально действующие процессы, smoke,
rollback и разницу между code available и feature active. Не нужен новый
вопрос «сливать ли?» для обычного полностью проверенного и ранее
согласованного изменения без новых побочных эффектов.

Это **не** GitHub Auto Merge, не фоновый deploy bot и не безусловное право на
операции production. Для включения постоянного Hermes Agent, новой модели,
потенциальных расходов, интеграций, новых секретов, внешней публикации,
пользовательских данных и высокорисковых изменений в действующих systemd/
firewall/DB по-прежнему нужен отдельный явный approval и доказанный security
GO. В случае препятствия пометить BLOCKED с конкретной причиной и
продолжить другие независимые безопасные задачи. Без pending/failing CI
merge запрещён. Не приравнивать установленную документацию к запущенному сервису.

## Передача и безопасность

В итоговом PR сообщить, какие критерии выполнены, тесты/проверенный SHA, что осталось не доказано, какие изменения происходили на VPS и кто разрешил их. Не закрывать задачу без необходимых доказательств.

Не устанавливать сторонние `SKILL.md`, исполняемые файлы или архивы на VPS по факту наличия в проекте. Не вводить второй контроллер, очередь, постоянный агент, новый источник состояния, unattended CI auto-merge/deploy bot, провайдера или доступ к private vault. Не переносить новостной поток YFC, права публикации и источники данных. Действующие `AGENTS.md`, модель угроз и owner gates имеют приоритет над этим руководством.
