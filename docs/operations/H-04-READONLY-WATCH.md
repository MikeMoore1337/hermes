# H-04 - отдельный контроль приватного GitHub CI с защитой от ложного восстановления

## Источники и права

[Issue #5](https://github.com/MikeMoore1337/hermes/issues/5). QA Advisor читает только приватный `MikeMoore1337/hermes`, ветку `main`, обязательный workflow `quality.yml` (ID `381262090`), максимум три GitHub Actions метаданных за запрос. Разрешён один точный HTTP GET на `api.github.com`, токен из root-owned `0600` файла `/etc/hermes-agent/github-actions-read.token`, без redirect, retry и GitHub write. Не читает сырые CI логи, данные YFC/Second Brain и содержимое PR. API-клиент предварительно проверен владельцем на VPS, 15.10.2026, результат SUCCESS.

## Связь с существующим Ops Watch

Новая ограниченная служба `hermes-qa-watch.service` только читает CI и **атомарно записывает минимальный статус** в `/var/lib/hermes-qa-watch/ci-signal.json`, владелец root, права `0600`. Состояние включает точные проверенные константы repository/workflow, завершение, run_id, SHA и timestamp. Никаких заголовков, URL, названий PR, авторов, журналов и токенов. Новая служба не имеет Telegram-токена, нет возможности прямой отправки сообщений, записи в новости или изменения GitHub.

Существующий `hermes-ops-watch.service` остаётся сетево изолированным; после проверки root-owned CI signal он может добавить только ранее разрешённый код `ci_failed` в общую SQLite-очередь. Существующий `hermes-ops-alerts.timer` доставляет **один** инцидент за запуск тем же ранее утверждённым частным Telegram-ботом. Источник сигнала - только Hermes main, не YFC. Тексты сообщений - каталог фиксированных кодов, ничего из GitHub не подставляется.

При `FAILURE` без предыдущего активного CI инцидента создаётся `new`. После нового подтверждённого `SUCCESS` создаётся `resolved`. `UNKNOWN`, `RUNNING`, HTTP 401/403/404/429/5xx, stale signal более 32 минут и отсутствие файла **не** закрывают предыдущее событие. Долгое отсутствие связи требует отдельной ручной проверки; не считать такое состояние «здорово». Монотонный run_id не разрешает подтверждать восстановление более старым успешным запуском или неожиданным success на том же run_id, где уже зафиксирован FAILURE. Это гарантия наблюдаемой последовательности в текущем узком workflow, не доказательство, что все ветки/проекты здоровы.

## Запуск, проверка, откат

Код, юниты и tests проходят GitHub CI и проверку checksum до установки. Источники отдельно копируются как точные blob в `/opt/hermes-agent-owner`. Команда подготовки (установка только после owner GO на отдельную read-only службу):

```bash
sudo bash /opt/hermes-agent-owner/deploy/install-qa-watch.sh
systemctl status hermes-qa-watch.timer --no-pager
journalctl -u hermes-qa-watch.service --no-pager -n 20
```

Установщик проверяет исходные три действующих таймера, root-only token, чистую проверку без `--execute`, systemd verification и **один** настоящий GET перед включением таймера. Прямое обращение из обычного процесса разрешено только при явном `--execute`. Планировщик запускает раз в 15 минут, `Persistent=false`; никаких массовых догоняющих запросов.

В начале deployment, пока signal неизвестен, Ops Watch не создаёт CI событие. После включения таймера требуется отдельно проверить последовательность автоматических запусков, рабочий SQLite journal и что существующие YFC новости не изменены. **Никаких искусственных красных workflow в приватном Hermes ради теста не создавать**. Тесты переходов с подменой статусов выполняются исключительно во временных каталогах и с mock API.

Откат нового считывателя (не отключает новости/существующие Telegram alerts):

```bash
sudo systemctl disable --now hermes-qa-watch.timer
```

До отключения убедиться, что `hermes-qa-watch.service` не обрабатывает запрос. **Не** применять `systemctl disable` к связанному через symlink `hermes-discovery.timer` (ранее был инцидент с удалением unit symlink). Если новый sampler надолго выключен во время реального активного CI инцидента, Ops Watch **не** создаёт ложное восстановление от устаревшего/отсутствующего статуса. Для отмены кода integration отдельный PR и стандартный CI.

## Ограничения

- Не проверены свежие сборки YFC, сторонние workflow/branch, job logs, реальный root cause и общий GitHub API rate-limit между другими потребителями.
- Нет права GitHub write, PR/Issue creation, job rerun, auto-fix, deploy, публикации или сохранение исходного API body.
- При сбое сети наблюдение может прекратиться; таймер продолжит обычные редкие проверки, **без ускоренных ретраев**.
- Раньше владелец отдельно подтвердил реальный Telegram `message_id=4` на тестовом инциденте. Подтверждение **естественного** CI-инцидента и реального `resolved` через этот новый источник требует будущего факта, а не только моделирования.

## Обновление #717: метаданные GitHub Observe для Operator Inbox

Первые разделы выше описывают **исходную** службу CI с одним GET.
В согласованной интеграции #717 тот же 15-минутный systemd таймер и
тот же токен \`Actions: read\` используются для **второго**
фиксированного запроса к API GitHub Actions, только к workflow
\`Hermes GitHub event observe (no executor)\`, ID \`403765637\`.
Список ограничен 12 последними запусками; максимум 10 сообщений в
обезличенном снимке, не старше 24 часов, TTL 45 минут.

Дополнительный запрос имеет таймаут 5 секунд, основная проверка CI -
12 секунд; прежний \`TimeoutStartSec=22s\` и установленный systemd
unit **не изменяются**. Сбой второго запроса не отменяет запись
успешного/неуспешного CI signal, а старый GitHub feed со временем
получает статус \`STALE\`.

Существующий root-owned снимок QA \`0700/0600\` независимо
проверяется штатным root-owned Control Center snapshot collector,
после чего владелец видит лишь фиксированные события и статусы в
\`/api/operator/inbox\`. Сам UI web-сервис не получает права
доступа к токену или исходному root-only файлу, не делает GitHub
HTTP-запросы и не запускает команды.

Это **наблюдение, а не команда для Hermes**. Полный GitHub журнал
и автоматические запуски задач не появляются. После PR/merge/CD
реальную загрузку feed и отображение в production Inbox подтверждать
отдельно; исходники и зелёные тесты сами по себе не доказывают
свежую запись на VPS.
