# H-02: ручная проверка свободного места без очистки истории

Связано с Issue #117 и PR #115. После снятия ограничения 1000 исторических ACK SQLite может продолжать расти. Автоматическая очистка/архивация запрещена до отдельной утверждённой политики хранения и проверенного восстановления.

## Ручной запуск

Из корня актуального клона репозитория на Linux-хосте, где разрешён доступ к защищённому каталогу Ops Watch:

~~~sh
python3 -m ops_watch.storage_capacity
# {"status": "NOT_EXECUTED"}
python3 -m ops_watch.storage_capacity --execute
# 0: OK; 1: REVIEW; 2: UNKNOWN
~~~

Инструмент проверяет только метаданные каталога (0700), регулярного SQLite-файла (0600), владельца, количество hardlinks и statvfs для файловой системы. **Не открывает SQLite**, не выполняет SQL, не пишет, не удаляет историю или ACK, не читает токены и не использует сеть. Выводит только агрегированные размеры в байтах и заранее заданные коды. UNKNOWN нельзя считать OK.

Статус REVIEW возникает при SQLite **от 128 МиБ** либо свободном месте **не более max(2 ГиБ, 10% файловой системы)**. Это ранние ориентиры, а не доказательство повреждения и не распоряжение очистить файлы. При их превышении оператор отдельно оценивает резервные копии, свободное место, рост базы и срок хранения квитанций.

**Ограничения:** нет проверки SQLite integrity, скорости роста, содержимого очереди, WAL/journal, доставки Telegram или работоспособности восстановления. Нет автоматического VACUUM, DELETE, truncate, PRAGMA, рестарта, systemd timer или сообщений. Установка на production требует отдельного owner gate. В репозитории остаётся только необязательная read-only утилита.

## Тесты

~~~sh
python3 -m unittest -q tests.test_ops_watch_storage_capacity
~~~

Тестировать в Linux: нормальное/малое свободное место, крупный файл, пороги, symlink, hardening permissions, отсутствующий DB, ошибки statvfs, недопустимые счётчики и отсутствие утечки исключений. Все сценарии работают с временными фикстурами.
